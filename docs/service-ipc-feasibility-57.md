# #57 transient service and IPC synthetic feasibility

**Verdict: PARTIAL.** On this host a user-manager transient service launches Node without a caller handing a preexisting workload PID to the manager; a Unix stream socket can exchange messages, and its cgroup shows the requested limits and contains a detached descendant. This is not proof of an isolation boundary, crash-safe lifecycle, or compatibility with existing Node fork IPC. No production code, policy, data, privilege or deployment was changed.

## Experiment

Host systemd 259.9, Node v26.12.1, cgroup v2, user manager already `degraded` before and after. Before the test, the user-manager and app.slice `cgroup.subtree_control` both already included cpu, memory, pids; enabling controllers can otherwise affect sibling units (installed `systemd.resource-control(5)`). One unique unit, `hermes57-5fa81775b5c54e2a948bbf35172edba4.service`, with invocation `a254347383754f3eab12bc26689e7198`, was started with `systemd-run --user`, `Type=exec`, `MemoryMax=128M`, `TasksMax=64`, `KillMode=control-group`, `TimeoutStopSec=2s`, `RuntimeMaxSec=25s`, `Delegate=no`. The only data were synthetic. A mode-0700 temporary directory contained a mode-0600 Unix socket and throwaway Node code. No socket activation or inherited nonstandard FD was tested.

The service's Node process PID 929140 reported PPID 2051, independently identified as `/usr/lib/systemd/systemd --user`; `systemctl` reported the same MainPID and the service-specific cgroup. Thus, in this run systemd started the workload directly; the caller did not hand off a preexisting PID. A Node `net` connection to the pre-listening socket sent JSON with the service PID, child PID and cgroup, and responded `pong` to `ping`. Its detached, setsid descendant PID 929147 reported the same cgroup; `cgroup.procs` listed exactly these two PIDs. Manager properties and cgroup kernel files independently reported memory.max 134217728 and pids.max 64. This checks configuration, not actual enforcement under limit exhaustion.

Both test processes registered SIGTERM handlers. `systemctl --user stop` returned after 2.133 seconds; afterward neither PID existed in `/proc`, and the cgroup path had disappeared. Manager reported `ActiveState=failed`, `Result=timeout`, as expected for a stop requiring timeout escalation; success of the stop command did not mean success status. Neither disappearance nor a completed stop job proves the rigorous incarnation-bound `populated 0` release criterion in the scope research. Finally the exact unit was stopped/reset; readback showed `LoadState=not-found`, `ActiveState=inactive`, `MainPID=0`, and the socket directory was removed. The unit's RuntimeMaxSec was a bounded fallback; the harness also used `finally` cleanup. Temporary harness: `/home/itsara/.hermes/cache/scratch/service-feasibility-57.py` (scratch may be pruned).

## IPC and security caveats

- This demonstrates application-level bidirectional Unix socket messaging, **not** the existing Node `fork`/`child.send`/`process.send` JSON IPC channel, inherited handles, disconnect semantics, backpressure, or serialization compatibility. `server/src/workspace/process-driver.ts` uses `fork` with `stdio: ['ignore', 'ignore', 'inherit', 'ipc']` and `serialization: 'json'`; socket adaptation or a validated descriptor handoff and protocol redesign is needed.
- Installed `systemd-run(1)` documents `--pipe` passing standard FDs 0/1/2 as-is and waiting synchronously; it does not establish arbitrary Node fork IPC descriptor compatibility. Installed `systemd.exec(5)` and `systemd.socket(5)` describe socket activation/named descriptors and `StandardInput=socket`, but those approaches were not exercised. Direct socket connection shifts the problem to endpoint authentication, setup and lifetime. Permissions and random names do not exclude a hostile same-UID process; do not treat them as an authority boundary.
- Installed `systemd.kill(5)` describes control-group SIGTERM then SIGKILL after the timeout. `systemd.resource-control(5)` describes MemoryMax and TasksMax mapped to memory.max and pids.max. Actual cgroup migration prevention, controller enforcement, concurrent start/stop, launch errors, orphan handling and descendant escape were not tested.
- The user manager is shared by the UID; a same-UID hostile peer may access the user bus, socket, process or files. `Delegate=no` alone does not prove cgroup immutability or principal separation. Broad system-manager/polkit rights and arbitrary transient unit properties require separate narrow authorization and negative testing under distinct principals. Unit name/InvocationID lookup followed by stop is not an atomic conditional stop.
- Type=exec confirms exec startup, not application readiness, admission linearization or durable recovery. A manager-owned service eliminates the specific externally-created workload PID-to-scope handoff in this synthetic path; it does not solve in-flight launch ambiguity, manager failure, name reuse, crash fencing, reliable termination proof, or capacity release. These remain blockers described in `scope-lifecycle-authority-research.md`. No privileged or adversarial tests were performed on the shared host.
