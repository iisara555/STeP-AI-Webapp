# Cloud document slice: design blocker (#60)

No production document behavior is added by this investigation. #60 depends on #59 and asks for private chat drafting, editing, saving, Word download and restart persistence. Cloud currently hides document controls (`web/src/gateway.ts`), returns empty documents and rejects `session.draft`, `document.create`, upload and download. The Cloud `RuntimeCalls` contract has conversation operations only; `runtime-main.ts` calls the engine in `chat` mode. The Supabase `Host` and `session.draft`/document operations are not evidence of a Cloud persistence or export contract. The legacy `Host.download(path)` alone does not identify a Workspace or establish authorization. The gateway must not expose arbitrary filesystem paths or use the standalone migration archive as an authenticated service.

## Smallest proposed production tracer

First agree on the pinned Desktop engine's public draft representation and lifecycle, including how a chat draft is generated, edited, persisted and exported without bypassing its privacy/authority policy. Then implement one private Workspace draft end-to-end through the existing web Host, authenticated gateway, RuntimeManager admission/revocation and private runtime call seams. Resolve ownership from the authenticated identity and Workspace, never a user-supplied owner or direct path. Restrict document identifiers and sizes; enforce authorization at dispatch and response delivery, including revocation races. Use the supported engine interface for durable storage; do not write its SQLite schema directly. Keep UI controls unavailable until the entire selected operation is supported.

Before coding, resolve: (1) which pinned engine interface supplies draft creation, edits and stable IDs, and whether a draft belongs to a session or is an independent artifact; (2) concurrency/conflict behavior for edits and autosave; (3) whether Word is exported in the browser or runtime and how its safe, bounded payload is transferred; (4) disk quota and crash/atomicity requirements; (5) error and unsupported-version behavior. The issue does not specify these interfaces, and the current runtime contract does not provide them. Migrating Supabase personal and shared documents is separate: source ownership, sharing and target mappings require explicit decisions; importing an archive does not establish a permitted runtime API.

## Synthetic verification

`test/gateway-host.test.ts` uses the Cloud Host with a real gateway, a synthetic identity and a held runtime. The snapshot makes gateway requests, but its empty `documents` array is supplied by the Host. The Host rejects `session.draft`, `document.create`, upload and download locally with `CLOUD_NOT_AVAILABLE`; those document operations do **not** reach the gateway. The test guards this Host behavior rather than testing direct gateway requests.

The gateway's public HTTP contract has no document action dispatcher or document upload/download routes. There is therefore no defined direct gateway document operation to exercise; invented URLs or action payloads would not establish rejection of all possible bypasses. Direct malicious gateway requests are not covered by this test. This is **not** proof of document privacy, persistence, Word export, restart behavior or production host isolation. A future implementation must add direct gateway tests for its actual document routes, including owner, other user, admin, unauthenticated and revocation-race cases, plus restart/crash persistence and actual Word content checks with synthetic data and no live provider.
