# Bounded native launch-request adapter (not installed)

`native/quota-broker/launch-request.{c,h}` connects a real authenticated Unix
stream request to `qb_launch_workspace` and a trusted synchronous fixed-policy
launcher callback. It is a library, **not a root service or production runtime
composition**. The existing quota service and gateway production refusal are
unchanged. No real account switch, runner launch or XFS mutation is enabled.

## Deliberately bounded API

One `qbl` represents **one pre-established launch slot**, not a general launcher.
Trusted startup supplies the broker, fixed peer UID, user/workspace UUIDs,
prepared identity, fresh random 128-bit incarnation and launch ID, and fixed
launcher callback/context. The peer can supply none of those policy choices.
IDs are canonical lowercase hex and must be generated by trusted startup, never
chosen/recycled by workloads. There is no executable, argv, path, UID, environment,
quota identity, runtime secret, tmpfs-size or FD field on the wire.

The only exact frames (75 bytes including newline, followed by write EOF) are:

```text
LAUNCH/1 <incarnation-32hex> <launch-id-32hex>\n
STATUS/1 <incarnation-32hex> <launch-id-32hex>\n
```

The library serves a caller-owned, already-connected AF_UNIX SOCK_STREAM socket
with NONBLOCK and CLOEXEC. It verifies kernel `SO_PEERCRED` against the fixed UID
before any read, parse or reply, rejects ancillary data including SCM_RIGHTS,
requires exact length plus EOF, and uses an absolute monotonic 500ms deadline.
It rechecks expiry inside the core's synchronous callback, immediately before
invoking the launcher, and after synchronous work before replying. Deadlines
cannot cancel a blocked mutex, quota operation, fsync or in-flight launcher.
A slow trusted callback still blocks revoke by design; no asynchronous queue or
cancellation is allowed. The caller must bound accepted connections and invokes
one request per slot at a time; concurrent slot requests fail rather than queue.
This increment has no listener/accept loop and inherits no service-exhaustion claim.

UID is the trusted gateway principal, **not end-user authentication**. Workloads
must not share or inspect its account, memory or FDs. Startup must protect socket
endpoints and ancestors; the library cannot infer filesystem endpoint ancestry
from an accepted FD. Protected callers must join/drain every request before
`qbl_close`, and close all slots before `qb_close`. Do not close/reenter the core
or allow cancellation from the callback.

## Durable outcome, never blind replay

Trusted operator-only `qbl_establish` exclusively creates `launch.outcome` in a
protected 0700 state directory, after lifecycle census. `qbl_open` **never creates
or repairs missing state**. A regular, single-link, owner-only 0600 record binds
the exact principal, UUIDs, identities and IDs. An exclusive lifetime flock
rejects another adapter opener. State-directory ancestors/replacement and the
absence of an alternate authority remain trusted startup obligations.

Before calling the core, the adapter writes and fsyncs PENDING. Only then can the
core invoke the trusted launcher, under the **same core mutex as revoke**. The
borrowed workspace FD expires before core unlock. Completion is synced before
reply. Callback errors are always uncertain, even if errno looks retryable.

Replies are `LAUNCH/1 <outcome>\n`:

- `EMPTY`: status only, no attempt yet.
- `STARTED`: callback returned success; **not** proof of exec, runtime health,
  cgroup ownership, continued life or later process absence.
- `DENIED`: no actual launcher callback was entered (including expired admission).
- `UNKNOWN`: callback error, recovered PENDING, or live journal I/O uncertainty.

A replay of either verb only reports the recorded result; it never calls the core
or launcher again. Losing the reply does not erase the result. A crash at/after
PENDING may strand an attempt as UNKNOWN even if nothing spawned: conservative
availability loss, not exactly-once execution. A live write/sync failure poisons
the slot. Missing, truncated or mismatched records refuse open. No peer reset,
record deletion, ID rotation, garbage collection, new-slot issuance or retry API
is supplied. Trusted lifecycle reconciliation must prove absence and capacity
release **before authorizing another slot**, including a different ID. Merely
changing an ID or observing launcher exit is not reconciliation.

## Why no production launcher default

`native/runner-launcher` requires the runner's real/effective/saved UID/GID and
restricted supplementary groups; its one fixed bwrap policy consumes workspace
FD 1, secret stdin and a protected launch-ID socket directory. The broker runs as
a different privileged principal. Calling `srl_launch` directly would fail its
credentials check and exec away the broker; forking/queueing it after core unlock
would break this fence. The transport socket must never become runtime stdin.

No missing helper is replaced by sudo, shell, arbitrary exec, peer FD delegation
or an apparent successful enqueue. `qbl_open`/establish with no trusted launcher
callback return `ENOTSUP`. The service registers no callback. The synthetic test
injects a fixed launcher only; it does not establish runner-account support.

## Evidence and exact production gates

Unprivileged `test-launch-request.c` reports **12 named scenarios** using actual Unix connect/accept child peers
(and asserts their kernel PID), fake quota/launcher adapters, and a real durable
record. It covers completed revoke denying spawn, callback success/error,
disconnect during callback and lost unread reply, reopen/replay, process exit
inside callback recovering UNKNOWN, failed record fsync, missing/truncated state,
exclusive slot lock, mismatched principal/incarnation/ID, wrong UID before read
and without reply, short/oversized/extra-byte frames, missing EOF timeout,
SCM_RIGHTS, invalid/non-CLOEXEC/blocking/non-stream FDs and unsafe record paths/modes.
A mutex wrapper/barrier proves revoke observes EBUSY inside the transport's
callback, then sees the borrowed FD already closed on acquisition. A clock seam
expires admission during core observation and proves no launcher callback runs.
Additional scenarios send the frame in one-byte writes, expire the deadline after
callback success (STATUS/replay recover STARTED without spawning again), and fail
the completion fsync (live UNKNOWN, no retry). For the latter, this filesystem
retains the written STARTED byte across reopen; a power loss can instead leave
PENDING/UNKNOWN. Neither terminal recovery authorizes another callback. These
fault seams are not a power-loss durability simulation.
