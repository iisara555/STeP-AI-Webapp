# Supabase inventory before retirement (#65)

Read-only research for issue #65 (parent #56). Source: branch `integration/cloud-workspace-migration` at
`694383d`, compared with `main` at `344e185`. `main` is an ancestor of this branch, and `git diff main 694383d`
is empty for `supabase/`, `scripts/{bootstrap,import-harness,operator}.ts`, `web/src/host.ts` and
`web/src/auth.ts`, so every Supabase line reference below is valid on both branches. No Supabase project, live
service, `.env` file or secret was read; environment variables are listed by name only.

## สรุปสำหรับเจ้าของโครงการ

**ตอนนี้ยังปิด Supabase ไม่ได้** ระบบเว็บเดิมยังพึ่ง Supabase เกือบทุกส่วน ส่วน Cloud Workspace ทำแทนได้แค่บางส่วน
และยังเป็นการทดสอบด้วยข้อมูลจำลองเท่านั้น

สิ่งที่ Cloud **มีทางทดแทนแล้วในโค้ด** (แต่ยังไม่เปิดใช้จริง เพราะ gateway ยังปิดไว้จนกว่า #57 เสร็จ):

- เข้าสู่ระบบด้วยบัญชี Google ขององค์กร และเชิญ/ถอนสิทธิ์ผู้ใช้
- แชตและประวัติแชตแบบส่วนตัว แยก Workspace ของแต่ละคน
- โควตาจำนวนงานต่อวัน และพื้นที่เก็บรายคน 15 GiB (ยังไม่ได้ติดตั้งบนเครื่องจริง)
- บันทึก audit แบบไม่เก็บเนื้อหา
- เครื่องมือย้ายประวัติแชต (ทดสอบกับข้อมูลจำลองเท่านั้น)

สิ่งที่ **ยังไม่มีทางทดแทน** (ช่องว่าง):

1. เอกสาร ไฟล์ที่อัปโหลด และร่างเอกสาร Word (#60)
2. ความจำ (memory) ของผู้ใช้ และเครื่องมือย้ายความจำ
3. โปรไฟล์และรูปแบบผู้ช่วยของแต่ละคน
4. อ่านใบเสร็จ (OCR) — โมเดล OCR ที่วางแผนไว้ยังไม่ได้ติดตั้ง
5. เชื่อม Google Drive / Calendar (#61) — ผู้ใช้ต้องเชื่อมใหม่ ไม่ย้าย token เดิม
6. Skills และความรู้องค์กรในหน้าเว็บ Cloud (#59) — ยังซ่อนอยู่
7. งบ AI รายเดือนและหน้าสรุปการใช้งานสำหรับผู้ดูแล (#50, #58)
8. หน้าดู audit สำหรับผู้ดูแล
9. การแชร์ Workspace ให้คนอื่น — เจ้าของตัดสินแล้วว่ายังไม่ย้ายข้อมูลที่แชร์ไว้
10. สำรองข้อมูลจริงนอกเครื่อง (#62) — ซ้อมแล้วแค่ข้อมูลจำลอง
11. ค้นหาในเนื้อหาแชต (Cloud ค้นได้แค่ชื่อแชต)
12. ชุดติดตั้งเว็บสำหรับใช้งานจริงแบบ Cloud (ไฟล์ติดตั้งปัจจุบันยังบังคับใช้ Supabase)

ข้อที่ **ตรวจจากโค้ดอย่างเดียวไม่ได้** และต้องให้ผู้ดูแลดูในระบบ Supabase เอง: มีข้อมูลจริงกี่รายการ ตั้งค่าใน Dashboard
อะไรไว้บ้าง มีการแก้ระบบจริงนอกโค้ดหรือไม่ และ Supabase สำรองข้อมูลไว้แบบไหน (ดูหัวข้อ 6)

ข้อเสนอ: ให้ Supabase ทำงานตามปกติต่อไป ปิดได้เมื่อ (1) ทุกช่องว่างข้างบนมีทางทดแทนหรือเจ้าของอนุมัติให้ทิ้ง
(2) ย้ายข้อมูลและตรวจครบทุกชุด (3) ซ้อมย้อนกลับสำเร็จ และ (4) เจ้าของอนุมัติเป็นลายลักษณ์อักษร หลังจากนั้นเก็บ Supabase
แบบอ่านอย่างเดียวไว้อีกช่วงหนึ่งก่อนลบจริง เอกสารนี้ไม่ได้แตะหรือเปลี่ยนข้อมูลจริงหรือบริการจริงใดๆ

## 5. Draft decision criteria, acceptance checks and rollback

### Decision criteria (all must hold before proposing retirement)

1. Every gap in section 3 is either replaced in production or explicitly accepted as dropped/deferred by the owner
   in writing (record it in `docs/migration-decisions.md`).
2. #57 isolation, #58 identity/quota, #62 backup/restore and #64 pilot acceptance are complete on the production
   host, not only in synthetic tests.
3. A full encrypted backup of the Supabase database **and** the Storage bucket exists offsite (database backups do
   not include Storage objects, `docs/operations.md:28`) and a restore of it was tested.
4. The data checks in section 4 pass with zero unexplained differences.
5. No other system uses the Supabase project (checked in the Dashboard and with the team).
6. The owner approves the retirement separately (#65 acceptance criterion 4).

### Acceptance checks at cutover

- Freeze: Supabase made read-only (writes refused for `authenticated`; worker and cron stopped) and verified by a
  refused test write; no active runs.
- Reconciliation: section 4 report reviewed and signed by an administrator.
- Users: every migrated user signs in to Cloud, sees their private history, and cannot see another user's data
  (spot checks plus the #64 five-user test).
- Backup: the first scheduled Cloud backup after cutover completes and a restore drill succeeds.
- Deployment: the public web build no longer contains `VITE_SUPABASE_*`; Google OAuth redirect URIs for Supabase are
  removed only after the read-only period.

### Rollback plan

- During the read-only period, Supabase stays intact and read-only; nothing is deleted.
- Rollback trigger: failed acceptance check, data mismatch, or security finding.
- Steps: (1) point the web build back to the Supabase build (`VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY`,
  without `VITE_GATEWAY_URL`); (2) re-enable writes and the worker/cron; (3) stop the gateway or keep it fail-closed;
  (4) list any work done in Cloud during the attempt and ask users to re-enter it, because there is no Cloud-to-Supabase
  sync; (5) record the cause and rerun the rehearsal (#64).
- Rehearse this rollback in an isolated environment with synthetic data before the real cutover (#64).
- Final deletion of the Supabase project happens only after an agreed retention period and a last verified export,
  with a separate owner approval.
