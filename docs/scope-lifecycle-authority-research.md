# #57 — principal-separated scope lifecycle authority: design, not deployment

**Status: BLOCKED / proposal.** No authority, production integration, privilege change, or workload was deployed. This is an implementable protocol contingent on the isolation and termination-proof gates below, not evidence that those gates work. Existing experiment: `/home/itsara/projects/step-scope-cleanup-prototype/spikes/057-scope-supervisor/RECOVERY-BLOCKER.md` (sibling checkout). Its reported synthetic reproduction shows identical unit and cgroup names reused with different InvocationIDs. Identity-check-then-StopUnit is not conditional stop.

## Evidence and what it does _not_ establish

- Local systemd 259.9 user and system manager introspection expose `StartTransientUnit(ssa(sv)a(sa(sv))) -> o`, `StopUnit(ss) -> o`, and `GetUnitByInvocationID(ay) -> o`. Stop takes no invocation precondition; the unit-object `Stop(s)` likewise has none. See [systemd manager/unit D-Bus API](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.systemd1.html), also installed `org.freedesktop.systemd1(5)`. A lookup by invocation ID followed by stop has the same race. A unit object path is not a documented generation-bound stop capability.
- `StartTransientUnit` requires a unique name while creating the transient unit, which is released when no longer running or referenced, or at reboot. `fail` is a _job-conflict_ mode, not a permanent no-reuse reservation. Start/stop replies return an asynchronous job path, not completed work. Subscribe before issuing the call and correlate `JobRemoved` by job path; `done`/other results and connection loss must be handled. `UnitRemoved` means unloaded, not independently proof of death. Source: same API, StartUnit/StartTransientUnit/Signals sections. `RefUnit` exists, but neither its presence nor a reference is evidence of a durable, exclusive incarnation lock; references must not be relied on after authority/bus death without separate proof.
- Scope units group externally created processes; unlike services they do not fork them, have no main process, and remain based on existence of scope processes, not leader status ([systemd.scope(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.scope.html)). Descendants must not escape via cgroup or other privileges. `KillMode=control-group` kills remaining group processes on stop; `none`/`process` can leave them alive ([systemd.kill(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html)). Confirm actual properties and scope support on target versions, not just defaults. `Delegate=` permits a private cgroup subtree; it is not a boundary preventing escape if the workload can write outside its allowed subtree ([systemd.resource-control(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)).
- PID 1 manager mutation methods are protected by `org.freedesktop.systemd1.manage-units` polkit authorization ([D-Bus API security](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.systemd1.html)). This is an authorization action, not a demonstrated safe narrow grant for arbitrary transient properties. User managers are per UID ([user@.service(5)](https://www.freedesktop.org/software/systemd/man/latest/user@.service.html)). A same-UID hostile user-bus peer is outside the exclusive-authority assumption. Read access is generally allowed; a unit name is **not a secret**. Manager version on this host and method signatures alone do not demonstrate any cross-principal denial.
- Read-only local checks: `systemctl --version` reported 259.9; `systemctl --user is-system-running` reported `degraded`; both buses answered introspection. No synthetic mutation was performed for this research; the prior reproduction is reported by the sibling experiment, not independently rerun here. `busctl --user get-name-owner` is unsupported by this local CLI; determine current D-Bus unique owner with `org.freedesktop.DBus.GetNameOwner` and watch `NameOwnerChanged` in a real implementation. A unique bus name is connection-scoped, not a durable manager identity.

## Security boundary and privileges

Trust PID 1/systemd, kernel, root/host administrators, the storage stack and a single independently protected authority principal. Treat runtime manager, workload, all other UIDs and all concurrent callers as potentially compromised; distinguish authorization of a manager client from authorization of a particular operation. Root or another actor with manager/cgroup authority can violate the invariant: this design does not defend against a malicious host administrator.

Recommended candidate: a dedicated protected authority service account/process with only the host-admin-provisioned system-manager permissions it demonstrably needs, serving an authenticated narrow Unix socket. Host policy must deny the client/workload system-manager creation, stop, restart, attach, property modification and other lifecycle control for this namespace, access to authority credentials/state, ptrace/signals, and writable cgroup ancestors; it must also prevent manipulating the authority's manager, executable/configuration, or impersonating the principal. Run workload under a different UID with no writable relevant cgroup hierarchy. A dedicated private user manager under a different UID is another candidate, not automatically secure: its login, bus, signals, ptrace, lifecycle, cgroup and filesystem boundaries all require validation. Root authority is technically possible but increases blast radius; broad `manage-units` or transient-unit properties can amount to extensive host control. An install-time privileged policy may be necessary; **no such policy is supplied or assumed proven**. Don't grant a client generic D-Bus forwarding, arbitrary PIDs, arbitrary properties, unit names, commands, paths or UIDs.

Authenticate socket peers with kernel credentials (`SO_PEERCRED`) and restrictive directory/socket permissions, then map peer identity to allowed workspace operations in protected policy; UID alone is insufficient if unrelated processes share it. Bind the authenticated subject and workspace to each operation. A same-UID workload/client implies this authentication cannot distinguish them; provision distinct principals or use a stronger separately validated mechanism. Never accept a caller-selected process for scope inclusion. Use bounded, versioned requests and per-operation idempotency keys; replies and logs must not expose provider grants. A nonce/name is an identifier, never authority.

## Authority ownership and state

Only one authority instance may issue systemd mutations: hold an OS exclusive lock on a protected local lock file from before state validation until the D-Bus connection and all spawned launcher helpers are closed. No failover based on timeout/lease alone. Open lock and state under an authority-owned, non-writable-by-others directory with no symlink traversal; validate owner/type/mode/filesystem and reject corruption. Prevent child inheritance of the lock FD. An old helper or queued D-Bus message could survive the authority process: the design requires an explicit fencing proof before the next owner can mutate, including helper death, bus disconnect/queued requests and outstanding jobs. OS lock alone does not fence a surviving helper or an already accepted asynchronous job. If this proof cannot be made, restart remains fenced rather than assuming exclusive ownership.

Use a local durable transactional store with verified filesystem durability (e.g. SQLite with tested full synchronous durable commits, protected DB/WAL/SHM, appropriate locking, no unsafe network FS). In one serializable write transaction: validate current store epoch/schema/integrity, enforce global and per-subject capacity constraints, allocate a 256-bit CSPRNG operation ID and unit name `step-<64 lowercase hex>.scope`, insert a permanent non-reusable tombstone and reserve capacity, then commit before any process or D-Bus side effect. A unique index is mandatory; collision => generate again and retry transaction, never attach to an existing unit. Randomness prevents accidental collision/targeting but does not create exclusive control. Do not recycle names even after terminal state or across boot/store restore; tombstones or an equally strong non-reuse scheme must survive backups. Store protected installation epoch, boot ID, manager endpoint/observed owner generation, authenticated subject/workspace, operation ID, exact unit name, requested limits, state, observed InvocationID/cgroup when available, and audit evidence. Validate all fields and bindings before action. Storage rollback, restore, lost rows, full disk, fsync failure, incompatible schema, unreadable or conflicting rows fence admission; detecting missing entire storage/rollback needs an external durable anti-rollback anchor or operator reconciliation, not SQLite integrity alone.

## Protocol and crash gaps

States `RESERVED -> LAUNCHING -> RUNNING -> STOPPING -> VERIFIED_EMPTY -> RELEASED`; any state can enter `UNKNOWN` while retaining capacity. Persist `LAUNCHING` before sending any launch operation, and `STOPPING` before stop. Transitions are conditional on current state/version in the same transactional store. Serialize launch/stop/recovery per operation and global admission in the authority; persist enough request/result information for duplicate calls to return the same operation, without spawning twice. Disconnect, timeout, client death, D-Bus failure, ambiguous error or lost reply never implies no side effect.

1. **Launch gating:** The authority, not the untrusted client, creates a minimal trusted launcher initially blocked on a one-shot gate before exec/fork of any workload. Define precisely where the launcher runs and ensure parent death closes the gate and the launcher exits; no escaped workload may execute in the pre-scope window. Create the transient scope using only that authority-owned launcher's validated process identity and fixed allowlisted properties. PID reuse and child death during D-Bus handoff require a proven pidfd-capable path or an equally robust verified handoff; if systemd's target interface only accepts numerical PIDs and atomic binding is unproven, this is a blocker. The launcher must not be externally triggerable, inherit authority secrets/socket/lock, or fork descendants before confinement. This is not equivalent to letting a client provide a PID. Wait for the correlated job and validate same manager/boot, unit identity, limits, cgroup membership and fresh InvocationID, then durably record RUNNING before opening the gate. If anything is uncertain, never open the gate and retain reservation until verified cleanup. Alternative transient **service**, where the manager itself starts the process in the unit, may remove the externally-created scope/PID handoff gap but changes IPC and runtime semantics and requires independent research and approval.
2. **Stop:** authorize authenticated subject against the durable record; revoke runtime access first, transactionally set STOPPING, then while holding exclusive lifecycle authority check boot/manager generation, name, InvocationID, cgroup and expected properties. If identity disagrees, quarantine; never stop a mismatched unit. Issue StopUnit for the non-reused name, correlate its job, then prove termination under the predicates below. The lookup and stop are safe against replacement **only if the separately enforced exclusive lifecycle invariant holds throughout**, including authority crash/restart and in-flight jobs; the InvocationID check is defense in depth, not a CAS.
3. **Proof and release:** Before committing VERIFIED_EMPTY, establish that the exact target incarnation cannot be recreated, all its processes stayed confined, no start/attach can be in flight, and its entire cgroup subtree is empty. Read `cgroup.events` `populated 0` from a verified cgroup-v2 mount and safely opened target, with trusted ancestors and no writable migration path. A path disappearance, missing unit, empty ControlGroup, zero InvocationID, signal loss, failed job, inaccessible or malformed events, or manager owner change is _unknown_ unless a separately validated authority-specific proof covers that exact case. A completed stop job by itself is insufficient to prove descendants gone. Persist VERIFIED_EMPTY with its proof and then transactionally release capacity exactly once; a crash between commits is safe and retryable. Capture/validate mount ID and safe path resolution, account for cgroup removal races, and avoid claiming an open FD alone gives immutable incarnation identity without evidence.
4. **Recovery:** new owner obtains exclusive lock, establishes old actor/helper/job fencing, validates store and reconciles every nonterminal record before admission. For LAUNCHING with unknown send/reply, it cannot infer that a missing unit means no process was ever launched; distinguish (a) durable pre-send state with proven no side effect, (b) observed exact live unit, and (c) ambiguous absence. Only (a) with proven no helper/in-flight request or (b) followed by valid termination proof may release; (c) remains UNKNOWN. RUNNING/STOPPING similarly reconcile against boot, actual manager generation, invocation and scope; no trusting caller-provided unit name. If a restart/reboot prevents proof, fence. A different boot can support a special release rule only after proving host reboot kills all prior workloads and state is not transplanted/rolled back, and explicitly validating mount/host identity and manager provenance; it is not assumed here.

## Integration with existing lifecycle contract

`server/src/workspace/contract.ts` requires `startWithAdmission` to call `admit` synchronously around the actual spawn, and `stopWithAdmission` synchronously around initial stop enqueue; `RuntimeStartCleanupError` retains a handle when startup cleanup is unconfirmed. A remote authority RPC is asynchronous and is **not** automatically compatible: invoking a socket write inside `admit` is not the same as the authority actually spawning or enqueueing StopUnit, and asynchronous authorization could occur after revocation. A redesign must establish an explicit linearization point across revocation and the authority (e.g. move the admission/revocation decision into the same authority and durable transaction, with a verified fencing protocol), or revise and prove the contract. Until then omit these optional methods and preserve fail-closed gateway behavior. In-memory manager capacity/handle ownership cannot be counted as durable across restart; do not release on `onExit`, a leader PID, or a lost IPC channel. Map unknown start to a recoverable durable handle/`RuntimeStartCleanupError`, unknown stop to failed stop with reserved capacity, and only report stopped after proven empty. Confirm this against `manager.ts` implementation before any integration.

## Required acceptance tests / unresolved blockers

- On an isolated disposable host, use two actual UIDs and negative tests for user/system bus direct create, stop, restart, attach, SetUnitProperties, cgroup writes/migration, signals/ptrace, state and socket impersonation; also test separate manager and hostile same-UID peers. No privileged test was performed here.
- Validate policy scope and transient-unit property restrictions, effective privileges, service startup/restart, authority crash with in-flight D-Bus and helper actions, and whether a secure pidfd launch handoff exists on each supported systemd/kernel version. Test manager reexec, bus restart/name-owner change and host reboot. No proof currently exists that a second authority can safely take over.
- Fault-inject SIGKILL/power loss at every durable commit, launcher spawn, scope registration, job signal, gate release, stop, verification and capacity-release boundary; fresh recovery knows only the store. Include simultaneous authorities and clients, duplicate requests, same-name replacement, malicious PID reuse, descendant forks/setsid, migration attempts, store corruption/deletion/rollback, ENOSPC/fsync errors, missing cgroup and delayed job completion. Assert no wrong-incarnation stop and no capacity release for UNKNOWN.
- Exercise the synchronous admission linearization with real gateway revocation races and demonstrate crash-safe capacity, then conduct independent security review. Until all gates pass, #57 remains a production blocker; this note authorizes neither deployment nor a claim of a working recovery mechanism.
