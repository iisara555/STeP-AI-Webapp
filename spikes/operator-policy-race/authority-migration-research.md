# Coordinated invitation authority: migration research (not an implementation)

## Decision and exact blocker

Do not wire or deploy a new store yet. A separate SQLite DB plus `user_version` does **not** fence the old binary. The unchanged `InvitationStore` never checks versions and creates its own `invitations` table. A legacy process pointed at a still-accessible old DB also authorizes independently of the new policy. A view named `invitations` can block this particular old store against the _new_ DB, but cannot stop a running or restarted process using the old DB, another copy, a stale file or an existing open handle. Separate DBs and a logical version marker alone therefore do not prove a single authority.

The repository supplies no implemented, demonstrated deployment mechanism that stops all legacy gateway processes and prevents their restart, closes/removes their old DB handles, revokes network ingress to them and restricts the coordinated DB to one writer identity. Nor is an authenticated operator administrative channel specified. The blocked production `main.ts` has no deployed system to inspect. A local SQLite prototype would silently assume away the very bypass we must exclude. No safe end-to-end migration can be claimed or implemented against the supplied seams until an operator-controlled cutover and ACL are specified and verified. No gateway code was changed.

## Threat model and trust boundary

- Protect against stale gateway requests and credential snapshots, concurrent operators/admins/gateways, crashes during migration or replacement, and accidental launch of a legacy executable against the new DB. A completed ceiling removal must not be followed by a newly admitted protected effect, even from a request authenticated earlier.
- Also protect against a legacy process continuing against the old DB: stop and fence **all** legacy binaries, handles, copies, ingress and supervisor restarts before activation; a DB-local check cannot protect a different DB. Restore or rollback must not re-expose the old authority.
- The operator is trusted to change the maximum set, but ordinary authenticated users, invitation admins and OS identities without operator capability cannot change the ceiling. Administrative invitation actions must not grant ceiling-management capability. An authorized operator intentionally removing everyone is allowed and must not be confused with uninitialized state.
- A compromised authority process, root/host administrator, DB-directory owner, or party able to alter authority executable, SQLite files, WAL/SHM, snapshots, IPC ACLs, or the deployment supervisor is outside this model. SQLite table constraints and the view are not protection against them. If a gateway process is untrusted it must not own or write the DB: a separate authority service with authenticated local IPC is needed. ACL configuration and deployment identity separation are prerequisites, not effects of a schema migration.
- Filesystem permissions must cover parent directories and database, WAL, SHM, backups, copies and symlink/path replacement; use a service-owned directory not writable by the gateway or tenants. Local IPC must bind in an authority-owned directory and authorize peer OS credentials; operators have a separate restricted capability from gateway requests. Verify denial with actual service identities, not just mode bits. Avoid exposing arbitrary SQL, DB paths or a generic signing capability. Specify an audited break-glass path and disable old mechanisms.

## Proposed cutover and atomic import contract

1. Inventory every gateway instance, supervisor, route, configured base file, admin/domain config, DB path/copy, and writer. Stop ingress and all legacy instances; disable restarts and revoke their DB and socket access. Confirm no old process or held handles and verify failed restart / failed ingress. Treat this as a hard precondition throughout the cutover. If exclusion cannot be proven, abort; a lock acquired once does not prevent later old starts. For this repository there is explicitly no production data/deployment, but any future migration must still satisfy the contract.
2. Read the source policy file and old DB only after quiescence, from trusted stable snapshots. The existing parser lowercases and splits on whitespace/commas; preserve that normalization. Validate the entire input and report invalid or duplicate/colliding entries without silently dropping them. Reconcile invalid legacy data explicitly rather than losing denials. Snapshot domain and admin sets too: current admin protections use constructor config, domains are lowercased, and membership is checked against the base. Detect conflicting configs among instances and fail before activation.
3. Explicitly invoke a one-shot import, never automatic on an ordinary service start. In a fresh authority DB, validate schema/identity and source inventory; within **one** `BEGIN IMMEDIATE` transaction insert the full initial ceiling, all old invitation rows including inactive denials, relevant normalized domain/admin config, metadata and an `initialized` marker/generation. Commit all or roll back all; a second import must reject unless a separately authorized recovery procedure is used. Check counts and exact normalized contents against snapshots before enabling ingress. Failure, crash or corruption must leave either no usable authority or the complete import, never an initialized partial set; restart checks marker, schema, integrity and identity and fails closed. An empty imported ceiling is a valid initialized, deny-all policy; absence of the marker is not an empty policy.
4. In that same new DB, reserve `invitations` as a deliberately invalid view and require the new code to verify both its own exact schema/version/identity and fence on each open. The view must be created transactionally at initialization, before exposing the path. It blocks the tested unchanged legacy reads/writes but is defense in depth only. No stale file is a live input after cutover; file edits must not be advertised as revocation.
5. Enable only the new service and ingress after import, fence and permissions checks. Remove or quarantine old DB/files with permissions that prevent legacy reuse. Never roll back to a live old gateway using a stale snapshot. Recovery must restore the latest coordinated state and fencing together; if unsure, leave ingress closed and re-import only via an explicitly reviewed procedure.

## Runtime semantics and ordering

- Effective membership is `ceiling minus durable active=0 denials`. Existing `active=1` records do not expand the ceiling. Preserve denials even while an email is absent from the ceiling; re-adding that email does not erase a prior admin denial. Keep domain validation, protected admins (cannot be toggled), admin actor must be an admin and currently effective, and activation cannot exceed the current ceiling. Credential validation and actor/effective-membership checks happen after acquiring the same ordering fence as mutation.
- Operator replacement validates the **entire** proposed ceiling/config before mutation and atomically replaces it in a writer transaction; rejected input leaves the old generation and contents unchanged. It serializes with admin mutation and protected dispatch. An authenticated operator acknowledgement occurs only after durable commit. An empty replacement commits deny-all. A successful removal prevents any protected admission linearized after that commit; actions admitted before removal may already have had effects and are not retroactively undone. Define how ongoing sessions/streams are closed or rechecked separately; do not claim rollback of delivered output, signals or spawned processes.
- Auth may use a snapshot only for preliminary rejection. Every security-sensitive commit/send/spawn/publish and admin change must recheck current effective membership and credential validity at its actual existing synchronous admission point. Fail closed on service/IPC/database failure and after loss of fencing. Do not accept stale generation as authority. Audit operator identity, committed generation and result without logging credentials.
- With one trusted direct-DB gateway identity, all writers must use the same lock and no other identity can write. If an isolated authority service owns SQLite, it must provide an explicit admission protocol which holds the ordering fence until the gateway's synchronous effect has occurred and been acknowledged; revocation cannot acknowledge while a prior admitted effect can still occur. Design timeout, process death, lost reply, replay, network partition and fencing so a disconnected/stale gateway cannot later perform an effect; do not hold a transaction across unbounded I/O. This hard distributed-systems requirement is **not implemented or proved** here. A separate service with a simple check-then-send API would recreate the race.

## Required tests before implementation can be accepted

- Test-first, real cross-process tests with timeouts/barriers, not sleeps: legacy binary opening new DB fails closed on invitation read, mutation and dispatch, including fresh connection and already-open connection; incompatible/missing/altered fence, schema, version, uninitialized or corrupt DB fail closed. Verify old binary cannot start or accept ingress under actual deployment identities, including a pre-open old handle and attempted restart. If old process can still act, fail cutover.
- Import: exact old-state parity, active and inactive rows, duplicates/case, invalid addresses/domains, empty ceiling, pre-existing target, mismatched configuration, transaction contention, injected failures and SIGKILL at each stage; restart sees complete committed state or no initialized authority. Import is one-shot. Crash-recovery tests must include SQLite WAL/SHM and no accidental empty initialization.
- Operator replacement races in two or more processes with dispatch and credential-validated admin mutation; test both lock orders and prove acknowledged removal prevents subsequent protected effects, stale admin snapshots fail, and no disallowed intermediate/partial replacement appears. Kill lock holder and test recovery. Invalid replacement leaves prior policy byte-for-byte equivalent. Verify re-add preserves denials, admin protection, ceiling and domain behavior.
- Probe deny/allow of gateway, operator, admin and unprivileged OS identities for DB, parent directory, WAL/SHM and IPC; test symlink/path swapping, copies/backups, peer credential spoofing and rejected arbitrary SQL. Test service crash, IPC timeout, stale queued request, reconnect, lost acknowledgement and held admissions.
- Preserve and run existing invitation/admin, auth and all gateway admission/dispatch/stream/revocation tests; replace file-live race tests only when the public operator contract explicitly changes. Exercise the full actual gateway integration and confirm production isolation refusal remains in place. No such compatibility or service-ACL results are claimed by these research probes.
